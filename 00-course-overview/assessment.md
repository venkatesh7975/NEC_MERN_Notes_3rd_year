# Assessment and submission guide

This is a proposed teaching policy, not official university grading. Faculty sets deadlines, accommodations and examination weights.

## Continuous assessment

Keep a personal log with activity ID, date attempted, source commit, expected result, actual result, status and next correction. Use dates of real work. A suggested balance is daily practice 20%, assignments 30%, practical demonstration 30% and explanation/reflection 20%; faculty must announce any adopted grading policy.

## Evidence

Each submission includes source, deterministic fictional fixtures, run instructions and an evidence table. Use Expected / Actual / Pass or Fail / Notes columns. Record failed cases as well as successful ones. Screenshots help UI review but cannot replace executable source or a query transcript.

## Difficulty and selection

Beginner projects isolate one concept; intermediate projects combine concepts; advanced work handles complex state and failures; industry exercises require operational limits and a reproducible handoff. The project bank is elective. Complete the roadmap selection before selecting portfolio extensions.

## Submission

Use your own fork and submit its URL plus commit SHA through the [course form](https://forms.gle/rLbFcq6srWqrWnWh9) when faculty requests. Keep real identifiers out of public fixtures. Declare external code or AI assistance and be prepared to explain and modify the solution in a viva.

## Review and resubmission

Use each assignment's 100-point rubric. Record criterion-level feedback and repeat the failed checks after revision. A suggested learning gate is 70/100 plus a working central behavior; this is not an official pass regulation. See [practical examinations](../assessments/README.md).
